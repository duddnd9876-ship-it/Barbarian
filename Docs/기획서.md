# 웹게임 기획·구현 계획서 — 가칭 `hex-claim`

## Context

문명5/6의 야만인 모드에서 착안한 **턴제 멀티플레이 땅따먹기 전략 웹게임**을 새로 만든다.

핵심 아이디어는 "**유닛 하나로 공격과 방어를 동시에 할 수 없다**"는 딜레마다. 전사가 기지 위에 있으면 기지는 안전하지만 아무것도 얻지 못하고, 기지를 비우고 나가면 남의 기지를 노릴 수 있지만 내 기지가 열린다. 모든 전사의 체력·공격력이 동일하므로 승패를 가르는 변수는 오직 **지형(험지 방어보너스)·체력 관리(기지에서만 회복)·상대 유닛의 위치 판단** 세 가지다. 이 세 축만으로 깊이가 나오도록 규칙을 짜는 것이 목표다.

기존 `Last-Sanctuary`(Unity)와는 **무관한 신규 프로젝트**다. 이 문서는 규칙 확정 → 기술 구조 → 마일스톤까지를 담은 착수 문서이며, `Barbarian` 레포로 프로젝트 위치가 정해져 `Docs/기획서.md`로 이관했다.

### 확정된 선택 (사용자 결정)

|항목|결정|
|---|---|
|턴 진행|**순차 턴** (문명식 라운드 로빈)|
|인원 / 맵|**2~6인 · 육각 그리드**|
|스택|**React+TS 클라이언트 / Node+TS+WebSocket 권위 서버** (→ 아래 "구현 현황" 참고: 1차 배포는 Firebase 연동 전 로컬 핫싯으로 진행)|
|프로젝트 위치|`duddnd9876-ship-it/Barbarian`|

## 구현 현황 (2026-08-11 기준)

- GitHub Pages는 정적 호스팅만 지원하므로, 온라인 대전을 담당할 Node+WebSocket 권위 서버 대신 **Firebase(파이어베이스)로 백엔드를 대체**하기로 했다. 파이어베이스 연동은 다음 작업으로 남아 있다.
- 이번 배포는 **M1 "로컬 핫싯" 마일스톤**에 해당한다: 규칙 엔진(`src/shared`)과 SVG 렌더링 클라이언트를 완성해 같은 화면에서 2~6인이 순서대로 턴을 넘기며 플레이할 수 있다.
- 안개(전장의 시야 제한, M3)와 재접속(M3)은 온라인 대전이 붙기 전까지는 의미가 없어 보류했다. 파이어베이스 연동 시 `view.ts`(시점 필터)를 추가하고, Firestore/Realtime DB 리스너로 각 플레이어에게 필터링된 스냅샷만 전송하는 구조로 확장할 계획이다.
- 턴 제한시간(45초)은 클라이언트에서만 카운트되며, 만료 시 자동으로 `END_TURN`을 보낸다. 로컬 핫싯 특성상 서버 검증 없이도 치팅 문제가 없다.

## 1. 게임 규칙

### 1.1 승패

- 플레이어는 **기지 1개 + 전사 1기**로 시작한다. 게임 시작 시 전사는 기지 타일 위에 있다.
- 적 기지 타일에 **방어 유닛이 없을 때** 내 전사가 그 타일에 진입하면 **즉시 점령**한다. 기지는 점령자 소유가 되고, 점령자는 그 기지에서도 회복할 수 있다.
- **탈락 조건 = 소유 기지 0개.** (시작 기지가 1개이므로 "기지를 뺏기면 패배"와 동일하다. 남의 기지를 뺏어 2개가 되면 목숨이 하나 늘어나는 셈이 되어, 확장 자체가 보상이 된다.)
- 마지막 생존자가 승리. 턴 제한(기본 60라운드)에 도달하면 **소유 기지 수 → 누적 가한 피해량** 순으로 판정한다.

### 1.2 맵

- **Pointy-top 육각 그리드**, axial 좌표 `(q, r)`. 거리는 cube 좌표로 계산.
- 지형 3종:

    |지형|이동력|방어보너스|비고|
    |---|---|---|---|
    |평지|1|+0%|기본|
    |험지|2|**+50%**|산림/구릉|
    |장애물|통행불가|—|산/호수. 맵의 약 8%|

- **기지는 반드시 평지에 배치**한다(보너스 중첩 방지). 기지 타일은 자체 **방어 +25%**를 준다.
- 맵 크기는 인원에 비례: `반지름 = 3 + 인원수` (2인 → r5·91칸, 6인 → r9·271칸).
- 시작 위치는 링 배치로 **서로 등거리**가 되게 배정하고, 각 기지 주변 1칸은 평지로 강제한다.
- 맵은 **시드 기반 결정론 생성**. 같은 시드 = 같은 맵 (리플레이·재접속·테스트에 필수).

### 1.3 턴

- 고정 순서 라운드 로빈. 탈락자는 건너뛴다.
- 턴 제한시간 **45초**. 초과 시 자동 턴 종료(그 턴은 아무 행동 없이 넘어간다).
- 한 턴에 유닛이 쓸 수 있는 **이동력 2**. 행동:
    - `MOVE` — 인접 타일로 이동, 지형 이동력만큼 소비. 남은 이동력보다 비싸도 **이동력이 1 이상 남아있으면 진입 가능**(문명 규칙 차용). 그래야 이동력 2로 험지를 넘어갈 수 있다.
    - `ATTACK` — 인접한 적 유닛 공격. 이동력 1 이상 필요, 실행 시 **그 턴 종료**.
    - `FORTIFY` — 이동/공격 없이 주둔. 다음 자기 턴까지 **방어 +20%**. 이동하면 즉시 해제.
    - `END_TURN` — 턴 넘김.
- 타일당 유닛 1기. 플레이어당 유닛 1기(영구).

### 1.4 전투 (결정론, 난수 없음)

```
유효전투력(unit, tile, 방어측여부) =
    BASE_STRENGTH
  × (1 + (방어측 ? 지형보너스 + 기지보너스 + 주둔보너스 : 0))
  × (0.5 + 0.5 × hp / HP_MAX)          ← 부상당한 유닛은 약해진다

R = 유효전투력(공격자) / 유효전투력(방어자)
방어측 피해 = clamp(round(BASE_DMG × R^1.5),    10, 100)
공격측 피해 = clamp(round(BASE_DMG × R^-1.5),   10, 100)
```

양측이 동시에 피해를 입는다. 방어자가 죽어도 **공격자는 전진하지 않는다**(전진하면 기지 점령이 뒤엉킨다).

수치 감각 (BASE_DMG=24, HP_MAX=100 기준):

- 평지 만피 vs 평지 만피 → 서로 24. 4~5합에 결판.
- 평지 만피 → **험지 만피** 공격 시 공격자 44 / 방어자 13. **험지 선점이 압도적**이므로 무리한 공격이 억제된다.
- 만피 → 반피 공격 시 공격자 16 / 방어자 37. 부상자는 반드시 물러나야 한다.

난수를 넣지 않는 이유: 순차 턴 + 유닛 1기 구조에서 운으로 게임이 끝나면 전략이 무의미해진다. `config`에 `randomness: 0` 토글만 남겨두고 기본 비활성.

### 1.5 체력과 부활

- **회복은 소유 기지 타일 위에서만.** 기지 위에서 턴을 시작하고 그 턴에 공격하지 않았다면 턴 종료 시 **+25 HP**.
- 기지 밖 회복은 0. (사용자 규칙 그대로)
- **유닛 사망 시 3턴 후 소유 기지 중 하나에서 HP 50%로 부활**한다(부활 위치는 플레이어가 선택).
    → 유닛을 잃으면 기지가 3턴간 완전 무방비가 되므로 사망 자체가 충분히 무거운 페널티다. 사망=즉시 패배로 하면 첫 교전이 곧 게임 종료가 되어 재미가 없다. **이 규칙은 플레이테스트 1순위 튜닝 대상.**

### 1.6 전장의 안개 (M3)

- 유닛 시야 2, 소유 기지 시야 3. 시야 밖 적 유닛은 보이지 않는다.
- 지형은 한 번 본 타일이면 기억(회색 처리), 유닛은 실시간 시야에만 표시.
- **이 게임의 핵심 긴장이 여기서 나온다** — "상대 전사가 지금 집에 있나, 내 기지로 오고 있나"를 모르기 때문에 나가는 판단이 도박이 된다. 안개 없이는 계산 문제로 전락한다. 우선순위는 M3이지만, **서버는 처음부터 플레이어별로 필터링된 상태만 전송**하도록 설계한다(나중에 끼워넣기 불가능한 구조라서).

## 2. 기술 구조

### 2.1 원칙

1. **권위 서버(예정).** 온라인 대전이 붙으면 클라이언트는 명령만 보내고, 판정은 서버(파이어베이스 함수 등)가 한다. 지금의 로컬 핫싯 모드는 클라이언트가 곧 유일한 "서버"다.
2. **규칙 엔진은 순수 함수.** `src/shared`는 React나 브라우저 API에 의존하지 않는 순수 TS라서, 나중에 서버 쪽(Cloud Functions 등)에서도 그대로 재사용할 수 있다.
3. **결정론.** 난수는 시드 기반 PRNG만 사용(맵 생성 전용). `Math.random()`·`Date.now()`를 규칙 엔진에서 금지 → 리플레이·재현 테스트가 공짜로 따라온다.

### 2.2 폴더 구조 (현재)

```
Barbarian/
├─ src/
│  ├─ shared/                  # 규칙 엔진 — 순수 TS, 의존성 0
│  │  ├─ hex.ts                # axial/cube 좌표, 거리, 이웃, 링, 스파이럴
│  │  ├─ config.ts             # 밸런스 상수
│  │  ├─ types.ts              # GameState, Unit, Tile, Command, Event
│  │  ├─ rng.ts                # 시드 기반 PRNG
│  │  ├─ mapgen.ts             # 시드 기반 맵 생성 + 시작 위치 배치 + 연결성 보장
│  │  ├─ combat.ts             # 유효전투력·피해 계산
│  │  ├─ rules.ts              # 이동가능범위, 공격가능대상, 명령 유효성 검사
│  │  ├─ reducer.ts            # applyCommand(state, playerId, cmd) → 결과
│  │  └─ __tests__/            # vitest 단위/시나리오 테스트
│  ├─ state/gameStore.ts       # zustand 스토어 (로컬 핫싯 게임 상태)
│  ├─ render/                  # SVG 헥스 보드, 좌표→픽셀 변환
│  ├─ ui/                      # 로비, 게임 화면, 종료 화면
│  ├─ App.tsx, main.tsx, index.css
├─ .github/workflows/deploy.yml
└─ Docs/기획서.md              # 이 문서
```

파이어베이스 연동 시 `src/shared`는 그대로 두고, 온라인 대전용 `net/`(Firestore 리스너·명령 전송)과 `view.ts`(시점 필터)를 추가할 예정이다.

### 2.3 상태 모델 (`src/shared/types.ts`)

```ts
interface GameState {
  seed: number
  round: number
  turnOrder: PlayerId[]
  currentPlayerIndex: number
  tiles: Record<HexKey, Tile>
  units: Record<PlayerId, Unit>
  bases: Record<HexKey, PlayerId>
  eliminated: PlayerId[]
  status: 'lobby' | 'playing' | 'finished'
  winner: PlayerId | null
  damageDealt: Record<PlayerId, number>

```

## 4. 검증 방법

### 4.1 규칙 엔진 단위 테스트 (`src/shared/__tests__`, vitest)

- 헥스 거리/이웃/링/스파이럴 — 알려진 좌표 쌍, 개수 공식으로 검증
- 맵 생성 결정론 — 같은 시드 두 번 생성 시 완전 동일, 기지 주변 평지 보장, 모든 기지 간 연결성
- 전투 계산 — 기획서 1.4의 3가지 수치 케이스를 골든 값으로 고정
- reducer — 잘못된 명령 거절, 이동/공격/회복/점령/탈락/부활 시나리오

### 4.2 수동 확인 (완료)

- 2인 로컬 핫싯 한 판: 로비 → 91칸 보드 렌더 → 이동 가능 범위 하이라이트 → 이동 → 턴 종료 → 턴이 정확히 다음 플레이어로 넘어가는지 Playwright로 확인.

## 5. 열린 결정 사항 (착수 후 판단)

1. **부활 규칙** — 3턴/50% 회복이 맞는지. M1 플레이테스트에서 결정.
2. **험지 +50%** — 지나치게 강해서 교착이 생기면 +35%로 하향 검토.
3. **6인 순차 턴의 대기 시간** — 견디기 힘들면 "예약 명령" 기능을 M4에 추가 검토.
4. **게임 이름** — `hex-claim`은 가칭.
